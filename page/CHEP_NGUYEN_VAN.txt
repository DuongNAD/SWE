████ KHỐI 1 — CÂU 2 PHẦN (b) — 0.3 ĐIỂM — CHÉP 100%, KHÔNG THAY GÌ ████

Đề nào cũng hỏi y hệt "who carries out testing at each stage and why".
Chép nguyên khối dưới đây là xong 0.3 điểm.

b. Who carries out testing at each stage/level, and why:

- Unit Testing is carried out by the DEVELOPERS, because they wrote the code and
  they are the only ones who understand its internal structure and logic.

- Integration Testing is carried out by the DEVELOPERS together with the TESTERS,
  because it verifies the interfaces between modules that were built by different
  people, and both technical and functional knowledge are needed.

- System Testing is carried out by the TESTING TEAM (QA engineers), because they
  are independent from the developers and can test the complete system against the
  requirements specification objectively.

- Acceptance Testing is carried out by the CUSTOMER and the END USERS, because only
  they can confirm that the system meets their real business needs.


████ KHỐI 2 — CÂU 2 PHẦN (a) — ~0.7 ĐIỂM — CHÉP 95% ████

Chỉ cần đọc đề xem nó mô tả gì rồi giữ nguyên khối này.

a. Types and levels/stages of testing required by the manager:

TYPES required:
- White-box testing at the unit level, because testing must focus on the internal
  program structure.
- Black-box testing at the higher levels, because testing must be based on the
  functional requirements.

LEVELS/STAGES required, from the smallest unit up to the fully integrated system:
1. Unit Testing: testing each individual component or module in isolation.
2. Integration Testing: testing the interaction between combined units or modules.
3. System Testing: testing the complete, fully integrated system to evaluate its
   compliance with the functional requirements.
4. Acceptance Testing: final testing based on user expectations and business needs.

   ⚠ Nếu đề KHÔNG nhắc tới người dùng nghiệm thu thì bỏ dòng 4.


████ KHỐI 3 — CÂU 5 DESIGN PATTERN — ~0.7/1.0 ĐIỂM — CHÉP 75% ████

Hai đoạn dưới đây chỉ phải thay MỘT chỗ: dòng "Applying it to this system".

⚠ TRƯỚC NGÀY THI phải hỏi giảng viên lớp dạy pattern nào. Nếu lớp dạy khác
   Singleton/Observer thì thay tên và định nghĩa, giữ nguyên bộ khung 4 gạch đầu dòng.

Pattern 1: Singleton Pattern

- Purpose: The Singleton pattern ensures that a class has only one instance and
  provides a global point of access to that instance.
- How it works: The class keeps a single private static instance of itself, makes
  its constructor private so that no other object can create a new instance, and
  exposes one public method that always returns that same instance.
- Applying it to this system: In this project, it can be used to manage
  <VÍ DỤ: the database connection / the system configuration manager>, so that all
  modules share one single connection instead of creating a new one each time.
- Benefit: This saves system resources and keeps the configuration consistent
  across the whole application.

Pattern 2: Observer Pattern

- Purpose: The Observer pattern defines a one-to-many dependency between objects,
  so that when one object changes state, all of its dependents are notified and
  updated automatically.
- How it works: The subject keeps a list of observers. Whenever the state of the
  subject changes, it calls the update method of every registered observer, without
  needing to know their concrete classes.
- Applying it to this system: In this project, it can be used to
  <VÍ DỤ: notify the store manager and the warehouse when the stock of a product
  falls below the re-order threshold>.
- Benefit: This keeps the system loosely coupled and makes it easy to add new types
  of notification later without changing the existing code.
